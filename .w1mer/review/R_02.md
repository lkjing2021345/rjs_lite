# Review: Task 02 — Expand standard library (remaining Array/Object/String methods)

## Verdict: issues

Three findings. The most material one (M1) is a spec deviation introduced by
this task: `String.prototype.match` ignores the `i` flag, so
`"HELLO".match(/hello/i)` returns `null` where the spec requires a match.
M2/M3 are medium-severity spec deviations; the rest are observations.

## Findings

### 1. [MEDIUM] `String.prototype.match` ignores the `i` flag of RegExp arguments

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.match"` (lines ~3003–3032)

**Issue**: When the argument is a RegExp object, the arm reads only
`source` and does the plain `s.find(&pattern)` search. The `flags`
property is never consulted. The sibling arms `RegExp.prototype.test`
(lines ~3395–3410) and `RegExp.prototype.exec` (lines ~3411–3444) in the
same file both read `flags` and lowercase both sides when `i` is present
— the established in-repo contract for case-insensitive search.
`match` (and `search`, see M2) deviate from it.

**Concrete example**:
```js
"HELLO".match(/hello/i)   // this impl: null; spec: ["hello", index:0, input:"HELLO"]
"HELLO".search(/hello/i)  // this impl: -1;   spec: 0
```

**Spec basis**: ES2024 §22.2.5.5 `String.prototype.match` —
`RegExp.prototype[Symbol.match](R)`, where `R` is the RegExp. Per
§22.2.6.1, matching honors the `i` flag (case-insensitive). A RegExp
argument with `i` must therefore produce a case-insensitive match.

**Test coverage**: The two added tests (`string_match_returns_null_when_no_match`,
`string_match_returns_first_match_with_index_and_input`, lines ~4772–4784)
both use string arguments, so the suite is self-consistent with the
implementation — no test would catch the missing `i` handling.

**Severity**: Medium. The `i` flag is the RegExp flag most commonly
combined with `match` in real code. This is a regression against the
file's own RegExp contract (test/exec both honor `i`), not a
pre-existing limitation.

### 2. [MEDIUM] `String.prototype.search` ignores the `i` flag of RegExp arguments

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.search"` (lines ~2983–3002)

**Issue**: Same as M1 — only `source` is read, `flags` is never consulted,
plain `s.find(&pattern)`. Spec ES2024 §22.2.5.10 (via `RegExp.prototype[Symbol.search]`)
requires `i` to be honored. `"HELLO".search(/hello/i)` → impl `-1`, spec `0`.

**Test coverage**: Both added tests (`string_search_finds_first_match`,
`string_search_returns_minus_one_when_missing`, lines ~4753–4762) use string
arguments; the `i`-flag path is untested.

**Severity**: Medium. Same root cause as M1; fix should land together.

### 3. [LOW] `String.prototype.match` with global-flag RegExp returns a single match, not all matches

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.match"` (lines ~3003–3032)

**Issue**: The `g` flag is also ignored. Spec: with `g`, `match` returns
an array of *all* match strings (no `index`/`input`); without `g`, the
first match with `index`/`input`. The impl always returns the single
first-match shape. `"abab".match(/ab/g)` → impl `["ab", index:0, input:"abab"]`,
spec `["ab","ab"]`.

**Note**: The task's own plan doc (`.w1mer/detail/02.md`, line ~74) flagged
"ES2020 changed `match` to use `Symbol.matchAll` when `g` flag is present"
as a known risk and listed the `g`-flag behavior as expected. The
implementation omits it entirely.

**Test coverage**: No test exercises the `g` flag.

**Severity**: Low. The `g` flag is less common than `i` in `match`
call sites, and the result shape is at least internally consistent.

### 4. [LOW] `String.prototype.codePointAt` counts surrogate pairs, not code units

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.codePointAt"` (lines ~2789–2811)

**Issue**: The impl advances `pos` in *char* units, so for a string
containing a surrogate pair, `codePointAt(1)` returns the code point of
the *second* char (the low surrogate), not the code point of the second
code unit. Spec ES2024 §22.2.5.1: `pos` is a code-unit index;
`"😀x".codePointAt(1)` → spec `100079` (the low surrogate unit),
impl `120` (`x`).

**Concrete example**:
```js
"😀x".codePointAt(0)  // both: 128512  (correct)
"😀x".codePointAt(1)  // impl: 120;   spec: 100079
```

**Test coverage**: The added surrogate-pair test
(`string_code_point_at_surrogate_pair`, line ~4690) only checks
`codePointAt(0)` on the emoji — the correct case. `codePointAt(1)` on a
string containing an emoji is untested.

**Severity**: Low. The surrogate-pair *combination* itself (the
hard part the plan called out) is correct; the off-by-one-unit at a
position *after* a pair is an edge case most code never hits.

### 5. [LOW] `Number.isSafeInteger` rejects values that are exactly ±2^53

**Location**: `src/interpreter.rs`, `call_native` arm `"Number.isSafeInteger"` (lines ~3337–3345)

**Issue**: The check is `n.abs() <= 9007199254740991.0` (2^53−1).
The spec range is [−(2^53−1), 2^53−1], so ±2^53 itself is
*outside* the safe range and should be rejected — and it is, because
`2^53 = 9007199254740992 > 9007199254740991`. On re-reading: the impl
is actually **correct** here. `9007199254740992.0 <= 9007199254740991.0`
is false, so `isSafeInteger(2^53)` → `false`, matching spec.
**Withdrawn** — no issue.

### 6. [INFO] `String.prototype.match` with an empty pattern returns `null`

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.match"` (lines ~3015–3017)

**Issue**: `if pattern.is_empty() { return Ok(Value::Null); }`. Spec:
`"abc".match("")` → `["", index:0, input:"abc"]` (an empty string
matches at position 0). The impl returns `null`.

**Test coverage**: No test exercises the empty-pattern case.

**Severity**: Low. Empty-pattern `match` is rare in practice; the
`search` arm handles the same case correctly (returns `0`).

### 7. [INFO] `Object.fromEntries` silently skips non-array pairs

**Location**: `src/interpreter.rs`, `call_native` arm `"Object.fromEntries"` (lines ~3192–3207)

**Issue**: The impl `continue`s on any pair that isn't an
`Internal::Array`. Spec: non-array entries are simply ignored (only
array-like entries with a `0`/`1` are used) — so the behavior is
**spec-compliant**. The added test
(`object_from_entries_ignores_non_array_pairs`, line ~4806) confirms
this. No issue.

### 8. [INFO] `Object.fromEntries` skips keys already marked non-enumerable

**Location**: `src/interpreter.rs`, `call_native` arm `"Object.fromEntries"` (lines ~3201–3204)

**Issue**: `if !target.non_enumerable_props.contains(&key)` — the impl
refuses to overwrite a key that is in `non_enumerable_props`. Since
`fromEntries` always creates a *fresh* plain object (line ~3184),
`non_enumerable_props` is empty at entry, so this guard is dead code in
practice. It only matters if a future caller reuses the object. Not a
bug; noted for the dual-purpose `non_enumerable_props` contract
(see R_01 finding 1).

### 9. [INFO] `String.prototype.replaceAll` empty-needle returns the original string

**Location**: `src/interpreter.rs`, `call_native` arm `"String.prototype.replaceAll"` (lines ~2954–2956)

**Issue**: `if needle.is_empty() { return Ok(Value::String(s)); }`. Spec:
`"abc".replaceAll("", "x")` → `"xaxbxcx"` (inserts between every char).
The impl returns the original. This is a spec deviation.

**Test coverage**: No test exercises the empty-needle case.

**Severity**: Low. Empty-needle `replaceAll` is rare.

## Architecture-Impact Note

- **New contract**: 10 new native methods registered via the existing
  `define_non_enumerable` + `call_native` dispatch pattern. No new
  helper functions, no new internal state, no changes to `value.rs`.
  The change surface is confined to `src/interpreter.rs`
  (`install_builtins` + `call_native`).
- **Moved contract**: None. The existing `Object.defineProperty`
  dispatch arm is reused by `Object.defineProperties` (line ~3236) via
  a direct `self.call_native("Object.defineProperty", ...)` call —
  this is a new internal call path (native calling native) that was
  not present before. It is safe because `defineProperty` does not
  re-enter `call_native` recursively.
- **New internal convention**: `Object.defineProperties` collects
  descriptors into a `Vec<(String, Value)>` and calls `defineProperty`
  per key. This means `defineProperties` inherits `defineProperty`'s
  non-configurable rejection behavior (a later descriptor on the same
  key with `configurable: false` will be rejected on the second call).
- **RegExp contract tension**: `match` and `search` read `source` but
  not `flags`, while `test`/`exec` read both. This is an inconsistency
  in the in-repo RegExp contract (M1/M2). A future fix should make
  all four arms consistent.

## Pre-existing problems (orchestrator only, not in archive)

- `String.prototype.charAt` / `charCodeAt` use `s.len()` (byte length)
  as the bounds check, not char count. For a string containing multi-byte
  chars, `charAt(s.len()-1)` may return a wrong char or a space. This is
  pre-existing (not introduced by task 02) and affects all string methods
  that use `s.len()` for bounds.
- `Value::to_primitive` (value.rs lines ~148–181) returns `Undefined`
  when an object has a callable `valueOf`/`toString` — it does not
  *call* them. This is a pre-existing limitation.
