# Review: Task 03 — Harden exception semantics (try/catch/finally edge cases)

## Verdict: ok

No blocking issues. The commit correctly implements all 8 edge cases from the
plan, the 15 new tests adequately cover the edge cases, and the parameterless
`catch {}` parser change is backward-compatible. Three low-severity observations
noted below.

## Findings

### 1. [LOW] No test for `finally` returning a value that replaces a pending `Throw`

**Location**: `src/interpreter.rs`, test module (lines ~4353–4616)

**Issue**: The commit message claims "finally throw/return/break/continue
override pending result." The override cases for `throw` (3 tests),
`return` (2 tests), `break` (1 test), and `continue` (1 test) are all
covered. The one missing combination is `finally { return X; }` where the
pending result is `Throw(v)` — i.e., `try { throw 1; } finally { return 2; }`.
The implementation handles this correctly (the `!matches!(finally_result,
Flow::Value(_))` guard catches `Flow::Return`), but no test locks this in.

**Spec basis**: ES2024 §15.14.2 — `finally` completes with a return
completing the `try` statement, replacing the pending throw.

**Severity**: Low. The implementation is correct; the test gap is a
robustness concern, not a correctness one.

### 2. [LOW] `finally_runs_when_try_throws_without_catch` does not verify `finally` ran

**Location**: `src/interpreter.rs`, test `finally_runs_when_try_throws_without_catch` (line ~4392)

**Issue**: The test sets `out = "finally"` in the `finally` block but only
asserts that the error message contains "1" (the thrown value). It does not
assert that `out` was set to `"finally"`. If `finally` were silently skipped,
the test would still pass. The test name implies it verifies `finally` runs,
but the assertion does not.

**Concrete example**:
```js
// The test's source:
try { throw 1; } finally { out = "finally"; }
// Assertion: error.to_string().contains("1")  // true even if finally skipped
```

**Severity**: Low. The test is not wrong — it correctly verifies the throw
propagates. It just doesn't verify the `finally` side-effect.

### 3. [INFO] `catch` parameter binding via `define` bypasses `mutable` flag

**Location**: `src/interpreter.rs`, `Stmt::Try` arm (line ~920)

**Issue**: `self.env.borrow_mut().define(param.clone(), v, true)` — the
catch parameter is always defined as `mutable: true`. This is spec-compliant:
a catch parameter is always reassignable within the catch block. No issue.

### 4. [INFO] `catch` parameter shadowing is correctly scoped

**Location**: `src/interpreter.rs`, `Stmt::Try` arm (lines ~917–924)

**Analysis**: The catch block runs in a new child `Env` (line 918), and the
catch parameter is defined in that child env (line 920). After the catch block
completes, `self.env` is restored to `previous` (line 923). This means:
- The catch parameter does not leak into the `finally` block or the outer scope.
- The `finally` block runs in its own child env (via `with_child`, line 934),
  so it sees the outer scope, not the catch scope.
- This matches the spec: the catch parameter is scoped to the catch block.

**Verification**: The nested-try test (`nested_try_finally_runs_then_inner_throw_wins`,
line ~4517) confirms that the inner `catch (e)` does not leak into the outer
scope — `out` is set to `"inner:2"` (the inner catch's `throw 2` is caught by
the outer catch, where `e` is the outer catch's parameter, not the inner one).

## Spec-Correctness Analysis

I derived correctness from the unchanged side (spec semantics, surrounding

### Edge case 1: Parameterless `catch {}` (ES2019)

**Parser** (`parser.rs` lines 128–134):
```rust
if self.eat(&TokenKind::Catch) {
    if self.eat(&TokenKind::LeftParen) {
        catch_param = Some(self.identifier()?);
        self.expect(&TokenKind::RightParen)?;
    }
    self.expect(&TokenKind::LeftBrace)?;
    catch_block = Some(self.block()?);
}
```
- `catch_param` is `Option<String>`, initialized to `None`.
- If `(` is present, an identifier is parsed and `catch_param = Some(...)`.
- If `(` is absent, `catch_param` stays `None`.
- The `{` is always expected.

**AST** (`ast.rs` line 26): `catch_param: Option<String>` — correctly
represents the optional parameter.

**Interpreter** (`interpreter.rs` lines 919–921):
```rust
if let Some(param) = catch_param {
    self.env.borrow_mut().define(param.clone(), v, true);
}
```
- If `catch_param` is `None`, no binding is created. The catch block runs
  without the exception value being bound. This is spec-compliant: the
  parameterless catch discards the exception.

**Test**: `catch_without_parameter_still_runs_catch_block` (line 4372)
confirms `catch { out = "caught"; }` works.

**Verdict**: Correct.

### Edge case 2: `finally` always runs

**Interpreter** (`interpreter.rs` lines 931–939):
```rust
if let Some(finally) = finally_block {
    if let Ok(finally_result) = self.with_child(finally)
        && !matches!(finally_result, Flow::Value(_))
    {
        result = finally_result;
    }
}
```
- `self.with_child(finally)` is called unconditionally when `finally_block`
  is `Some`. The `if let Ok(...)` guard means: if `finally` throws, the
  `result` is NOT updated (the `finally` throw propagates via `?` in the
  caller). If `finally` completes normally, its flow is checked.

**Spec basis**: ES2024 §15.14.2 — `finally` always runs, regardless of
whether the try/catch phase completed normally, threw, or returned.

**Tests**: 
- `try_catch_finally_handles_throw_and_runs_finally` (line 4354) — finally
  runs after catch.
- `finally_runs_when_try_throws_without_catch` (line 4392) — finally runs
  when try throws and there's no catch.
- `finally_runs_before_return_from_try` (line 4452) — finally runs before
  the function returns.
- `try_without_throw_runs_finally_only` (line 4551) — finally runs when
  try completes normally.

**Verdict**: Correct.

### Edge case 3: `finally` throw/return/break/continue override pending result

**Interpreter** (`interpreter.rs` lines 934–938):
```rust
if let Ok(finally_result) = self.with_child(finally)
    && !matches!(finally_result, Flow::Value(_))
{
    result = finally_result;
}
```
- If `finally` produces `Flow::Throw`, `Flow::Return`, `Flow::Break`, or
  `Flow::Continue`, the `result` is overwritten.
- If `finally` produces `Flow::Value(v)`, the `result` is NOT overwritten.

**Spec basis**: ES2024 §15.14.2 — the `finally` completion replaces the
pending completion if it is a return, throw, break, or continue. A normal
completion (a value) does NOT replace the pending completion.

**Tests**:

- `finally_throw_replaces_uncaught_throw` (line 4439) — finally throw wins.
- `finally_throw_replaces_try_return` (line 4501) — finally throw wins.
- `finally_return_replaces_try_return` (line 4469) — finally return wins.
- `finally_return_replaces_catch_return` (line 4484) — finally return wins.
- `break_in_finally_wins_over_try_value` (line 4567) — finally break wins.
- `continue_in_finally_wins_over_try_value` (line 4585) — finally continue

- `finally_value_does_not_override_pending_result` (line 4603) — finally

**Verdict**: Correct.

## Backward-Compatibility Analysis

### Parameterless `catch {}` parser change

**Before**: `catch` required a parameter: `catch (param) { ... }`.
**After**: `catch` optionally accepts a parameter: `catch { ... }` or
`catch (param) { ... }`.

**Parser change** (`parser.rs` lines 128–134):
- `catch_param` is initialized to `None`.
- If `(` is present, an identifier is parsed.
- If `(` is absent, `catch_param` stays `None`.

**Backward compatibility**: 
- Existing code `catch (e) { ... }` → `eat(&TokenKind::LeftParen)` returns
  `true`, identifier is parsed, `catch_param = Some("e")`. Same as before.
- New code `catch { ... }` → `eat(&TokenKind::LeftParen)` returns `false`,
  `catch_param = None`. New behavior.
- No existing code can break: the parser only accepts `catch (id) { ... }`
  before, and still accepts it after. The new `catch { ... }` form is
  purely additive.

**AST change** (`ast.rs` line 26): `catch_param: Option<String>` — was
`String` before (presumably), now `Option<String>`. This is a breaking
change to the AST type, but since the AST is internal (not a public API),
and the only consumer is the interpreter (which handles both `Some` and
`None`), this is safe.

**Interpreter change** (`interpreter.rs` lines 919–921):
- `if let Some(param) = catch_param` — handles both `Some` and `None`.
- If `None`, no binding is created. The catch block runs without the
  exception value.

**Verdict**: Backward-compatible. Existing `catch (e) { ... }` code is
unaffected. New `catch { ... }` code is additive.

## Architecture-Impact Note

- **Moved contract**: `catch_param` in `Stmt::Try` changed from `String`
  to `Option<String>`. This is an internal AST change, not a public API
  change. The interpreter's `Stmt::Try` arm now handles both cases.
- **New contract**: The `finally` block's flow is now checked against the
  pending result. If `finally` produces `Flow::Throw`, `Flow::Return`,
  `Flow::Break`, or `Flow::Continue`, it overrides the pending result.
  If it produces `Flow::Value`, it does not. This is a new behavioral
  contract for the `Stmt::Try` arm.
- **New contract**: `finally` always runs, even when the try/catch phase
  throws without a catch. Previously, if the try threw and there was no
  catch, the `finally` block may not have run (depending on the old
  implementation). Now it always runs.
- **No new helpers**: The change is confined to `parser.rs` (try_stmt),
  `ast.rs` (Stmt::Try), and `interpreter.rs` (Stmt::Try arm + tests).
  No changes to `value.rs`, `env`, or other modules.
