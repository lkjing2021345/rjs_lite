## Correctness analysis (derived from the unchanged side)

### Phase detection (lines 186–193)

The runner maps the engine's stderr to a phase:

```python
if err.startswith("SyntaxError:"):
    phase = "parse"
else:
    phase = "runtime"
```

**Engine contract** (`src/error.rs` Display impl, lines 113–130):
- `JsError::Lex` → `SyntaxError: lex error at {line}:{col}: {message}`
- `JsError::Parse` → `SyntaxError: parse error at {line}:{col}: {message}`
- `JsError::Runtime` → `{error_type}: {message}` where `error_type` is
  `Error` / `TypeError` / `ReferenceError` / `RangeError`

So any parse/lex error starts with `SyntaxError:` → mapped to `parse`. Any
runtime error starts with `{type}:` (not `SyntaxError:`) → mapped to
`runtime`. **Correct.**

### Type detection (lines 191–193)

```python
m = re.match(r"(\w+Error):", err)
if m:
    err_type = m.group(1)
```

For `SyntaxError: ...` → `SyntaxError`. For `TypeError: ...` → `TypeError`.
For `ReferenceError: ...` → `ReferenceError`. For `RangeError: ...` →
`RangeError`. For `Error: ...` → `Error`. This exactly matches the engine's
`JsErrorType::as_str()` output (lines 34–42 of `error.rs`). **Correct.**

### Mode selection (lines 145–154)

```python
if "module" in flags:      modes = ["module"]
elif "raw" in flags:       modes = ["raw"]
elif "onlyStrict" in flags: modes = ["strict"]
elif "noStrict" in flags:  modes = ["nonstrict"]
else:                       modes = ["nonstrict", "strict"]
```

This matches test262's flag semantics:
- `module` → run as module (only mode)
- `raw` → run raw (no harness)
- `onlyStrict` → strict only
- `noStrict` → non-strict only
- (none) → both non-strict and strict

The docstring states "ALL required modes must pass" — the loop returns `fail`
on the first mode that fails, and returns `pass` only if all modes pass.
**Correct.**

### Negative test handling (lines 195–202)


- Negative test that didn't fail → `negative-but-passed` ✓

All four outcomes are handled. **Correct.**

## Findings

### 1. [LOW] Stale docstring — type verification is claimed absent but present

**Location**: `run_test262.py`, lines 19–21 (docstring)

**Issue**: The docstring states:
> LIMITATION: the runner does not verify the requested JS Error `type`
> (e.g. SyntaxError vs TypeError). Phase is matched by mapping our
> lexer/parser errors -> parse, runtime errors -> runtime.

But the code (lines 200–201) DOES verify the type:
```python
if neg["type"] and err_type and neg["type"] != err_type:
    return ("fail", CAT_NEG_TYPE, "type %s!=%s" % (neg["type"], err_type))
```

The type verification is functional (derived from the engine's error output
format, which I verified above). The docstring is simply outdated — it was
likely written before the type check was added.

**Severity**: Low. Doc inconsistency, not a functional bug. The code is
correct; the docstring contradicts it.

### 2. [LOW] `read-error` category defined but never populated

**Location**: `run_test262.py`, line 58 (`CAT_READ` in `FAIL_CATEGORIES`),
line 140 (return `("skip", CAT_READ, ...)`), lines 301–302 (accumulation)

**Issue**: `read-error` is in `FAIL_CATEGORIES`, so it appears in the report's
`failure_categories` dict. But read errors are classified as `skip` (line 140),
not `fail`. The accumulation logic (lines 301–302) only increments `cat_counts`
when `res == "fail"`:
```python
if res == "fail":
    cat_counts[cat] += 1
```
Since `res == "skip"` for read errors, `cat_counts[CAT_READ]` is never
incremented. The category is always 0 in the report.

**Impact**: The report shows `read-error: 0` always, which is misleading —
it suggests read errors are being tracked but always zero. In practice, read
errors are rare (the test262 checkout is read-only and the files exist), so
the impact is minimal.

**Severity**: Low. Design inconsistency, not a functional bug. The category
could be removed from `FAIL_CATEGORIES` or the read-error path could return
`fail` instead of `skip`.

### 3. [LOW] Non-deterministic `--limit` ordering

**Location**: `run_test262.py`, lines 105–121 (`collect`), lines 274–275
(`files[:args.limit]`)

**Issue**: `os.walk` returns files in OS/filesystem-dependent order (not
guaranteed to be sorted). `--limit N` takes the first N files in that order,
which is non-deterministic across OS/filesystems. Two runs with `--limit 20`
on different machines could select different 20 tests.

**Impact**: For smoke runs (the stated purpose of `--limit`), this is
acceptable — you just want N tests, not a specific N. But it means smoke-run
results are not reproducible across machines.

**Severity**: Low. Acceptable for the stated use case. Worth noting in the
docstring if reproducibility matters.

### 4. [INFO] Benign race in `_inc_cache`

**Location**: `run_test262.py`, lines 70–78 (`load_include`)

**Issue**: The include cache (`_inc_cache`) is a shared dict. Multiple threads
could call `load_include` simultaneously for the same name. The `if name not
in _inc_cache` check and the subsequent write are not atomic. In CPython, the
GIL makes dict operations atomic, so this is safe in practice — the worst
case is two threads both reading the same file (redundant I/O, no
correctness impact).

**Severity**: Info. Benign race, no action needed.

## Module tests (documented limitation)

The docstring (line 22) states: "module tests: engine has no module system;
run as plain script (will essentially fail)". Module tests use `import`/
`export` syntax, which the engine doesn't support. When run as plain scripts,
they fail with parse errors. This is expected and documented. The runner
correctly handles this by running module tests as plain scripts (the `module`
mode falls into the `else` branch of the mode loop, prepending the harness).
